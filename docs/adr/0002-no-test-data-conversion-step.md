# 0002 — Test data has no conversion step

- **Status:** accepted
- **Date:** 2026-07-31 (recording a pre-existing decision)

## Context

Runner rows exist in two formats: authored CSV and a generated JSON mirror. The
obvious-looking design is a pipeline — convert CSV to JSON at run start, then have
the suite read JSON. Several frameworks do exactly that.

## Decision

There is **no conversion in the test path**. `TEST_DATA_SOURCE=json|csv` selects
which format is read, and the readers in `src/data/readers/` read that format
directly at runtime. `MultiFileDataReader` normalizes both to one row shape so a
spec sees the same object either way.

## Consequences

- A run has one fewer moving part, and a failure cannot be "the converter wrote a
  stale file". What you edited is what ran.
- Both formats must genuinely stay readable, so the CSV reader carries real type
  coercion (`TypeCoercionHelper`) rather than leaning on JSON's types.
- The normalization contract is load-bearing and easy to break by adding a column:
  a column added to the CSV that is not listed in `MultiFileDataReader`'s array
  fields yields a raw pipe-delimited **string** from CSV and a real **array** from
  JSON. The `req` column is currently in exactly that state.
- Nothing may write generated runtime data under `artifacts/`, and
  `src/data/runner/*.json` must never be hand-edited — it is regenerated by
  `npm run runner:sync` and verified by `npm run runner:check`.

## Revisit when

Never, unless a data source appears that genuinely cannot be read in-process (a
database or a spreadsheet API). Then the conversion belongs in an author-time
script that writes a committed file, not in the test path.
